# Security and backend audit — 22 October 2026

Scope: the repository at `8c23a6d`, including NBE, NFE integration, Security, Test, Docs and CI. This is a code assessment with local regression testing, not a certification or an assurance that no vulnerabilities remain. No production mutations or exploitation are authorized or performed.

Review began 22 October; final local validation completed 23 October 2026 (Asia/Dubai).

## Discovery and initial assessment

The backend is Hono/TypeScript with Drizzle on Cloudflare D1, optional private R2 storage, Resend mail delivery, optional Slack/Turnstile and a database outbox. NFE uses Next.js/React and supports both a Vercel build and Vinext/Cloudflare build. `Docs/Deploy.md` describes the active Vercel-to-Worker proxy; older README text describes the Cloudflare alternative. Existing schema migrations add query indexes and shared fixed-window rate counters. Tests use Vitest and migrated in-memory libSQL; browser suites use Playwright and axe-core.

Existing protections include cryptographic random magic links and sessions stored as hashes, atomic token consumption, server-side role and tenant checks, first-party HttpOnly session cookies, origin checks, parameterized queries, validated JSON, attachment MIME allow-lists, download disposition, default private API caching, structured request IDs, an audit log, retention, dependency checks and a retry outbox. Do not replace these working controls.

## Confirmed findings at the initial code review

Severity is contextual; these are code-level findings, not evidence of production compromise. The remediation and validation sections below are updated as work proceeds.

| ID | Priority / weakness | Evidence and impact | Planned remediation |
|---|---|---|---|
| S01 | High, CWE-400 | `files/routes.ts` reads the entire upload before checking actual size. Missing or misleading Content-Length allows unbounded allocation. | Bound actual streamed bytes; test absent and forged lengths. |
| S02 | High, CWE-613 / CWE-863 | `admin/routes.ts` promotes an existing client to staff without revoking its existing client session; disabling/changing staff access leaves issued magic links valid. `auth/service.ts` can unconditionally reactivate a user disabled between lookup and login writes. | Revoke old sessions/tokens atomically at privilege changes and prevent disabled-account reactivation. |
| S03 | Medium, CWE-362 | `leads/service.ts` checks duplicates before an unconditional insert. Concurrent submissions can create duplicate leads and notifications. | Enforce the existing 24-hour deduplication rule at the database write boundary. |
| S04 | Medium, CWE-362 / CWE-841 | Approval state is read before an unconditional approval insert; a concurrent cancellation/decision can leave an approval on a closed request. File-count checks have a similar race. | Database guards for state and upload quotas, preserving batch rollback. |
| S05 | High operational risk, CWE-703 | Missing production Resend credentials use ConsoleMailer, which resolves successfully; outbox rows become sent although no email was delivered. | Fail delivery explicitly outside development and retain retry state. |
| S06 | Medium, CWE-400 / CWE-532 | Resend, Slack and Turnstile lack timeouts; retries lack provider idempotency and jitter. Arbitrary errors are stored/logged and may include sensitive request material. | Bound external calls, use stable email idempotency keys, redact error classifications, fence leases and add bounded jitter. |
| S07 | Medium, CWE-200 | The rate-limit table stores raw IP addresses and login emails in keys, despite privacy documentation saying addresses are hashed. Audit hashes are unkeyed and reversible by enumeration. | Key identifiers with a dedicated secret and separate namespaces; preserve old data only until retention removes it. |
| S08 | Medium, CWE-20 / CWE-346 | Configuration silently treats misspelled APP_ENV as development, weakening cookie settings; arbitrary URLs/origins are accepted. Client IP falls back to caller-controlled forwarding headers. | Validate environment and deployed HTTPS origins, keep proxy trust explicit. |
| S09 | Medium, CWE-200 | Body/origin/session middleware can error before API no-store headers are installed. Public content can process a session and emit Set-Cookie alongside public caching. Proxy-generated errors lack explicit no-store. | Set defensive cache defaults before early failures; prevent public caching of cookie-bearing responses. |
| S10 | Medium, CWE-532 | Verification tokens remain in URL query/history during login. Secret scanning prints matching source lines, including the value it detects. | Remove tokens from browser history promptly and report paths/categories only in scanners. |
| S11 | Low / defense in depth, CWE-20 | Content segment validation uses inherited object keys; JWT reference verification accepts extra token segments and insufficiently validates temporal claims. | Own-key checks, strict compact-token structure and claims. |
| S12 | Medium supply-chain risk | Actions use moving major tags; security scan errors are conflated with vulnerability findings; no static-analysis job. | Pin verified action commits, retain least privilege, distinguish audit availability, add focused static analysis and security regressions. |
| S13 | Medium, CWE-367 / operational resource risk | Maintenance selects every stale row and deletes lead notes/parents separately without rechecking status. A concurrent recovery can lose a lead and notes. | Bound each category to 500 rows and recheck eligibility within atomic note/lead deletion batches. |

## Suspected risks and existing gaps requiring verification

- Staff MFA and malware scanning are explicitly not implemented. Do not describe the app as meeting NIST AAL2. A pending upload is currently downloadable; require an explicit deployment decision before enabling attachments for clients.
- A full script-source CSP needs testing on both rendering paths, font delivery and optional Turnstile; preserve the current UI while validating a report-only policy first.
- Repository rules/protections, deployed secrets, Cloudflare Access/WAF, D1 backups, account MFA and operational monitoring cannot be established from source alone. Do not claim these are configured.
- Live-site retrieval through the web reader was unavailable. Only passive public header/page requests may be used; no production sign-ins, submissions or automated attacks.
- Request detail comments/member lists are unpaginated; maintenance returns every expired record. Measure and bound work where a meaningful test demonstrates resource risk.
- No raw SQL string concatenation, shell execution from API input, arbitrary outbound URL from user input or unsafe rendering of user-controlled HTML was found in the initial route review. This is limited evidence, not a universal negative claim.

## Local validation results

- Backend type checking and all **143 tests** pass, including the existing query-plan guards. No indexes were added. Cleanup statements and outbox ordering use the existing indexes; the tests mirror the bounded query shapes.
- NFE lint/type checks, Vinext production build and the Vercel Next.js production build pass. Native compiler/Workers checks needed execution outside the Windows sandbox after access-denied errors; successful reruns used the same source and locked dependencies.
- All five migrations applied to a fresh **local** D1 database. Drizzle generation reported no missing schema changes. The Worker dry-run bundle succeeded, approximately 1,120 KiB / 196 KiB gzip. No remote migrations/deployments were run.
- Source plus Git-history secret-pattern scanning passed with redacted output. NBE and NFE production dependency audits each reported **0** advisories at the time checked.
- Full NBE development audit reported **4 moderate**, **0 high/critical** findings in the Drizzle Kit/esbuild chain. npm's proposed fix is a breaking downgrade to Drizzle Kit 0.18.1; it was not applied. These packages are development tooling, not Worker runtime dependencies. Re-evaluate upstream fixes regularly.
- All **three isolated browser suites pass**: contact, portal and accessibility, including stored markup rendered as escaped text and URL credential cleanup. A two-comment test timing issue was corrected to exercise the XSS case in a single submission; the final repeat passed all three suites.

Passive HEAD requests to the current public deployment returned 200 for `/` and `/portal`, 307 for `/portal/verify`, and the existing frame/base/form/object CSP, HSTS, nosniff and strict referrer policy. The live portal remains a preview. These observations do not validate the new branch in production. No production forms, sign-ins or attack traffic were sent.

## Remaining production actions and limits

Staff MFA, a malware scanner for pending uploads, full nonce-based script CSP, privacy export/deletion workflows, monitoring/backup automation and exercised SSO key rotation remain open. Unpaginated member/comment/detail collections remain a resource-growth risk; no response-shape changes were introduced without a frontend paging contract. Spam/abuse controls still need edge WAF/rate policies and configured Turnstile where appropriate. No load-capacity or latency SLO claim is made from local tests.

Before approved release, configure the dedicated privacy key and verified mail/proxy settings, deploy dual-format NFE first, apply the additive migrations, then deploy NBE. Existing raw rate keys/unkeyed hashes are not retroactively removed. Provider idempotency is bounded in time; Slack may duplicate after a crash. Regex secret checks do not establish that every historical secret format was covered. Repository protections, production secrets, account MFA, backup access and alert delivery were not changed or verified from source. Exact maintainer steps and rollback/incident procedures are in `operations-runbook.md`.
